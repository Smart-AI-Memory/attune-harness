## D25: the ten release decisions

Patrick ruled in two messages the same evening: "1 yes agreed, 2 lets talk
about what will be frozen and when? 3 October, the rest as recommended";
then, once the freeze had been laid out as a table with its two moments,
"confirmed, table and October reading but I'm not inclined to indicate more
than the month, go". The ten decisions are recorded under the note's
numbering.

**Decision 1, 1.0.0 and the deprecation of attune-ai are two events.**
1.0.0 is the stable core the README describes. The deprecation is its own
milestone with its own note and parity list, whose first rows are the Claude
Code plugin and the multi-agent workflows. See "Raised the same evening"
below: Patrick leans toward that milestone following within days of 1.0.0,
which changes what the parity list must say by then, not the ruling that
they are two events.

**Decision 2, what the freeze covers, and when.** Frozen means three things
at once: a written list, a test that fails on a non-additive change to
anything on it, and a deprecation rule for the change that is allowed
anyway. Additive changes stay free after 1.0.0: a new verb, a new optional
key, a new optional configuration field. A rename, a removal or a change of
meaning ships only with the old form still working for one minor release, a
`deprecations` entry in the envelope, and a changelog line. The list, as
Patrick confirmed it:

| Surface | What exactly | Guarded by |
|---|---|---|
| CLI verbs | The 28 verbs and their subcommands, their required arguments and exit codes | The envelope table and a verb-list test |
| Envelopes | Top-level keys, `schema_version`, the meaning of every `status` value, exit codes; values never | The 71 golden rows, once the eight gaps the table records are closed |
| Configuration and saved state | The memory config, the task and run records on disk, plan state schema 1 and 2, the scratch record from 3.4, the extension manifest and the accepted registry | Schema versions, and a fixture from the 1.0 era that `status` and `resume` must keep reading |
| Refusal texts | The user-visible words, contracts already under D20.1 | The gate tests |
| The Python API | `run`, `Task`, `Output`, `Check` and `Receipt`, their signatures, and `run`'s documented behaviour: once, never a retry | A test that runs the README's example as written |
| Protocols | MCP tool names and schemas per profile version; the A2A local profile | Pinned by protocol version and changed only with it |

Outside the freeze: envelope values, stderr text, module names, the
experimental features' contracts (their envelopes stay pinned; the
deprecation promise does not cover them, and the README says which), the
receipt layouts under `docs/`, and attune-ai's own keyspace, read as it is.
Two moments: the content freezes at `1.0.0rc1`, and from then a change to
anything on the list restarts the candidate as `rc2`; the promise takes
effect at 1.0.0. So 4.1 lands last before the candidate, after 3.4's record
and after 4.3's manifest fields. The saved-state fixture is a cycle the note
had not counted: 4.1 is three cycles, and the note's total is seventeen to
twenty.

**Decision 3, October.** 1.0.0 is targeted in October 2026. Patrick
indicates the month and nothing finer: no day for the candidate or the
release appears in any document, and no date in the README. The candidate
period ends when 4.6 has been observed, two weeks of dogfooding from the
candidate have produced no change to a frozen surface, and the findings-log
rows are in. The pushback is recorded with the ruling: decision 2's order
puts 4.3's four cycles before the candidate, and the period needs its two
weeks, so October holds only if 4.3's Windows cycle holds; if it slips, the
choice between a candidate without executable plugins, against D6, and a
later month is Patrick's when it arises, not now.

**Decisions 4 to 10, as recommended.** 4.3 stays on the 1.0.0 path and
precedes the freeze (4). The memory transition ends at 1.0.0 by freezing as
read the attune-ai formats the native reader reads, removing the `adapter`
reader and the `FALLBACK` exception together with the differential, and
keeping the fixture as the contract; the condition "once attune-ai stops
writing" is dropped, and the constraint now runs the other way: no change
to those formats on attune-ai's side without a Harness reader change first,
which Patrick owns on both sides and which is to be written down on
attune-ai's side too (5). `ship` and `reflect` stay in the README's roadmap
row as planned routes, reworded at 1.0.0 to say a new verb is additive (6).
Patrick's `memory serve` observations since September 22 are to be written
as a dated note under `docs/specs/native-memory/` before 3.3's first pull
request; they are still owed (7). One person who does not program walks
through the installed journey during the candidate period, observed, with
the receipt in `docs/journeys/`; Patrick names the person, still owed (8).
`memory-native`, native planning and building, and `fix` on Windows ship
under their labels; the status line reads release candidate at `rc1` and
stable at 1.0.0; the classifier moves to `4 - Beta` at `rc1` and
`5 - Production/Stable` at 1.0.0 (9). The readiness direction, the October
plan, the journey map and the phased plan are marked superseded in the
documentation index, kept as dated evidence, and read by the October 1
review for opportunities, not requirements (10).

## Raised the same evening, not yet ruled

After the rulings Patrick wrote: "I am leaning back towards a swift
deprecation of attune-ai... maybe the next day or week after releasing
attune-harness." Decision 1 stands, two events; what changes is the distance
between them, and so what must be true for attune-ai's users by 1.0.0. Two
meanings of deprecation are possible, and the next ruling, D26, chooses:

- **A notice.** attune-ai's last release carries a deprecation warning and
  points to Harness; a migration page lists what Harness carries, what it
  does not (the Claude Code plugin, the multi-agent workflows, attune-ai's
  memory writers and its MCP tools), and what a user does about each;
  attune-ai stays installable and stops receiving work. This is what
  deprecation means for a package, it is realistic within days of 1.0.0, and
  the migration page becomes a candidate-period cycle: documentation written
  from the parity list, honest about what is not carried.
- **Parity.** Harness replaces attune-ai for what Patrick uses daily before
  the notice goes out: the plugin, the workflows, the hydration. Under this
  meaning the parity list is 1.0.0's scope after all, the plugin and the
  workflows need design notes before they can be sized, and October is off.

Recommended: the notice, with the migration page written during the
candidate period and the parity list kept honest in it; the plugin and the
workflows follow in 1.x as the deprecation milestone's own work. What
decides between the two is what Patrick himself would lose the week after
1.0.0. The question to answer before D26 is which attune-ai pieces his own
daily sessions still depend on, the plugin's skills and hooks, the hydration
writer, anything else, because under D6's test those are the users who lose
something.
