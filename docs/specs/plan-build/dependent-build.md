# Task 5 — dependent feature execution

The accepted work request now carries fixed protected verification commands for
every task and the final artifact. The first dependent profile is an explicit
ordered chain: every later task names its predecessor, and every output has one
producer. Duplicate ownership, missing dependencies or absent verification block
before participant calls. Branching graphs and repeated edits of the same output
are outside this first profile; no existing workflow is removed.

Configured worker and distinct reviewer assignments use the existing participant
transport with an explicit build protocol. Worker proposals contain task identity,
dependencies and exact file outputs. The host owns scope, preimages, commands,
source evidence and revision binding. Native transport receives substantive work;
the host wraps its response with control identities. External and native dispatch
permissions remain explicit. A deterministic adapter does not invent a feature.

The `feature-build-v1` journal stays inside the existing work record and writer
lease. It contains prerequisite controls, one worker response per step, host file
effects, each task's protected check, final protected verification and a reviewer
response. Earlier outputs become evidence for later tasks. A failed protected
check stops continuation; generated tests and a positive reviewer cannot override
it. High review findings require revision. Unsupported or uncertain checks remain
blocked and cannot be silently repeated. Existing file reconciliation works on
this same journal; the standalone effect API cannot take it over.

Completed operations are reused on resume. The validator reconstructs their order,
role/step correlation, output scope, snapshot transitions and verification result.
A successful process exit only establishes success within that accepted command's
scope. It is not proof that an arbitrary check covers the user's intent. The
frozen first-journey oracle and Task 8 comparisons provide separate behavioral
evidence. Reviewer output remains attributed advice, not human acceptance.

The existing testing intake accepts a `completed-feature-v1` producer reference.
It derives exact scope, retains work/request/checkpoint/artifact/probe identities,
and checks the producer before accepting or reusing a test result. A new pytest
task still uses its existing acceptance, runner and durable output artifacts.
No second testing or decision store is introduced. The production build feature
is not installed or activated by these tests; disposable captured checkouts hold
all candidate application changes.

Validation includes actual subprocess participants, actual dependent file writes,
protected tests, misleading generated tests, all saved operation boundaries,
stale source/configuration, missing dependencies and verification, changed output
scope, high review findings, unknown effects and corrected current producer checks.
Native adapters are tested with injected transport only. Real model effectiveness,
the actual Spec collector bridge and installed verbs remain later boundaries.

## Checkout bounds

Build and repair snapshot the complete dedicated checkout, including Git
metadata and untracked files. The bound is 2,048 entries (files and directories;
Windows also records the root itself) and 16 MiB of total file content. Each
editable file remains limited to 64 KiB. Exceeding a bound refuses preparation;
no files are omitted to fit. The same entry bound applies when validating saved
manifests. Existing smaller snapshots keep their format and remain readable.
