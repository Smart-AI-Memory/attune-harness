# Spec authority: addendum, September 21, 2026

[The decision note](README.md) is a dated record and is not edited. This file
records what a review on September 21 found, and two rulings Patrick made that
day. Where the two differ, this file is the newer one.

The review checked the note's claims against `main` at `02ccdf3`, the branch
`wip/local-snapshot-2026-09-19`, and the Attune AI branch
`codex/shared-memory-adoption` at `b89f7953f`.

## What the review confirmed

- The capability map does assign "Spec human decisions" to Attune AI's workspace,
  and the plan-build design does forbid "a second competing approval authority".
- `spec_bridge.py` imports exactly the three Attune AI modules the note names.
- `spec/state.py` has `schema_version` and writes through `os.replace`.
  `pipeline/spec_reader.py` parses `<task>` blocks. All seven files in
  `.claude/plans/` on the wip branch carry `schema_version`.
- The four candidate modules are 1,874 lines together: `spec/workspace.py` 995,
  `elicitation/command_workspace.py` 504, `spec/state.py` 319,
  `pipeline/spec_reader.py` 56. Each has its own tests. What they import from
  Attune AI directly is narrow: `security.path_validation`,
  `elicitation.spec_intake`, `wizards.decomposer`, and each other. Following
  every import from the package root reaches 143 files and about 44,000 lines,
  but that counts what Attune AI's package imports pull in, not what these
  modules use.

## D8: the Attune AI bridges are dropped

Asked whether the modules that plug Harness into Attune AI still have a job
once Attune AI is deprecated, Patrick answered: "No you can remove them. We will
not be maintaining attune-ai except for maybe one more publish to. I will
announce that it will be deprecated in a suitable length of time."

`attune_bridge.py` (129 lines) and `memory_bridge.py` (116 lines) get a **drop**
verdict. Nothing else in the package imports either one. They are reached from
`scripts/check_code_rag_host.py` and `tests/test_code_rag.py`, which have to be
reconciled in the same change. (Corrected when the removal was made: this line
first also named `scripts/check_attune_bridge.py` and `scripts/qualify_pilot.py`.
Those use `examples/extensions/attune_bridge.py`, a different file that stays.)

This keeps R2 as written: no runtime `import attune` anywhere in the package,
with no exception for host bridges.

The removal changes `src/`, so it is not done here. It goes through a pull
request of its own with a review by a different model, as AGENTS.md requires.

## D10: memory is kept, and is a goal for the first stable release

Added later on September 21, after the rest of this file was merged. It settles
item 3 in the list below.

Offered three paths for memory once Attune AI is gone (adopt the adapter now;
ship the `memory` command as not available yet; drop memory), Patrick chose the
second and added: "re memory, I want it." Asked whether memory could join the
first stable release if its adapter reviews well, he answered: "yes, that
ordering matches what I meant but I would like to include memory if possible."

So:

- `memory_context.py` stops importing Attune AI now, so that R2 can pass. Until
  memory is live, the `memory` command says plainly that it is not available
  yet. Nothing already built is removed.
- Memory is not dropped. `attune.memory.harness_adapter` gets a row in Task 1's
  verdict table beside the Spec modules, under the same adopt, adapt, reference
  or drop ladder and the same different-model review (D5).
- If that verdict is adopt or adapt and the work fits, memory ships in the first
  stable release. If not, it ships in the release after. The review decides;
  nothing here promises a date.

The agreed order: first the bridge removal, this change to `memory_context.py`,
the CI check for runtime `import attune`, and Tasks 1 to 5; then the release
candidate period, with the non-programmer walkthrough; then the first stable
release and the Attune AI deprecation announcement.

What the adapter is, measured on the Attune AI branch at `b89f7953f`: 423 lines
with 560 lines of tests, added in `c170febaf`. It is a compatibility reader of
Attune AI's existing stores. It imports `memory.file_stash`, `memory.personal`,
`memory.session_stash` and `security.path_validation` from Attune AI, and two
contract modules from Harness. Like D4 for spec state, it reads the old format.

## D11: memory waits for Windows

Added on the evening of September 21, after [Task 1's verdicts](verdicts.md)
found that the memory adapter refuses to run off POSIX
(`harness_adapter.py:111`). Offered memory in the first stable release as
POSIX-only, or waiting for Windows, Patrick answered: "Wait for Windows."

Memory ships when it can read on Windows through a handle-based reader with its
own safety review. D10 stands: if that is ready for the first stable release,
memory is in it; otherwise it follows in the next. Work on the reader and
ranking may start on POSIX.

The same day Patrick asked for the standard library XML parser to be tested
against hostile plan files before Task 2. It was, and the result is in the
verdicts: no new dependency is needed.

## What is stale or missing in the note

1. **D7 never reached `main`.** The note says `pyarrow` and `jsonschema` "now
   declare compatible ranges". That is true on the wip branch only. `main` pins
   all four Voyage dependencies exactly, and 0.1.0 and 0.2.0 shipped that way.
2. **The Windows note has been overtaken.** It lists Windows build effects as
   open. Version 0.2.0 shipped a handle-based implementation,
   `windows_effects.py`, used by `work_effects.py` and `work_build.py` and
   labelled experimental. What remains open is qualification, not the
   implementation.
3. **Memory is not covered.** `memory_context.py` imports
   `attune.memory.harness_adapter`, which exists only on the unreleased Attune AI
   branch, and `memory_cli.py` depends on `memory_context.py`. With D8, R2 cannot
   pass until that import is gone too. What Harness memory becomes without Attune
   AI was undecided when this was written; D10 above settles it. It has its own spec, `shared-memory-adoption`, on the wip
   branch.
4. **The two products import each other.** On the Attune AI branch,
   `spec/workspace.py` imports `attune_harness.spec_handoff`. Adopting that
   module into Harness ends the cycle. Until then the order in which the two
   packages are released matters.
5. **The salvaged edits may no longer be uncommitted.** The note describes the
   September edits to `spec/state.py` and `spec/workspace.py` in
   `~/attune-salvage` as uncommitted. The branch received a Spec commit the same
   day (`2a0e0e5e3`). Task 1 should compare the salvage patch with the branch tip
   before reviewing either.
6. **The target version needs restating.** The note aims at a "second release
   candidate". What shipped were the final versions 0.1.0 and 0.2.0, classified
   Alpha. No release candidate has been published.
7. **There is no estimate.** The October plan's 270,000 working tokens were
   proposed on September 18, before this decision, and assume Attune AI stays
   installed as a runtime dependency. Nothing has sized the work in this note.
   Task 1's verdict table is the place to produce a first estimate, per module.

## Evidence that Spec and memory depend on unreleased Attune AI code

Published Attune AI is 16.4.0. It has no `harness` extra and no
`attune.memory.harness_adapter`. Codex's 27 unmerged test files that fail
against `main` were re-run on a scratch copy with the causes removed one at a
time. With local receipts supplied, and published Attune AI and the Anthropic
SDK installed, 62 tests still failed: 26 with a forms validation error, 23 of
them in `test_spec_handoff`; about 23 for the missing adapter; 11 needing a
change to `memory_native.py` that `main` lacks. That the 26 need the unreleased
Spec repair is a hypothesis and was not confirmed.
