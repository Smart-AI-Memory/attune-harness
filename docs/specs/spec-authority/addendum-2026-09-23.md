## D22: the executable plugins spec is approved, its six decisions as recommended

Later the same day, after [the spec](../executable-plugins/README.md) had
been through four passes of a different-model review under the brief with
every finding dispositioned in its pull request (#97), Patrick ruled:
"approve the plugins spec as recommended". The six decisions the spec
names are therefore settled as its recommendations state them:

1. **Signing.** GPG, through `gpg --verify` in a bounded subprocess against
   a keyring the host builds from the public key blocks the accepted
   registry carries, the maintainer's key first; the verdict is read from
   the status lines (`GOODSIG` and a `VALIDSIG` with a listed fingerprint,
   no expiry, revocation, bad or error line), never from the exit status
   alone; an absent or failing verifier is a refusal.
2. **`grants` and `declares`** as two manifest fields, a grant being a host
   action and a declaration anything the child could violate.
3. **The vocabulary of version 1:** the five grants (`secrets`, `paths`,
   `scratch`, `time`, `output`) and the six declarations (`imports`,
   `network`, `reads`, `writes`, `subprocess`, `vendored`), plus `revoked`
   and `signers` in the registry; anything else is manifest schema version 2.
4. **The child's import path:** the standard library, the bundle, and the
   closure of an `imports` declaration resolved by a finder the bootstrap
   installs, through the host's interpreter with `-I -S -B`; the finder is a
   cooperating bundle's guard against undeclared and supply-chain use, not
   isolation, and it is what lets Voyage be the first consumer under D7.
5. **The paid stage journal stays with the host**, written in `perform`'s
   order (`prepared`, then `dispatching` before the child starts), so a kill
   leaves `dispatching` and is refused rather than billed twice.
6. **Approval** is this ruling. Phase 3's exit condition "the plugin spec is
   approved" is met; the implementation is Phase 4's 4.3, four cycles.

The spec's one new base dependency, `packaging` for marker evaluation, is
accepted with it; the signing scheme adds none.

## D24: the stage mapping for Task 4, step (b)

Step (b)'s first half, the rename, found that the design note's sentence "the
two lifecycle gates `chair_required` and `blocked` that a high-severity build
result raises" does not match the code. The workspace has two gate kinds: the
lifecycle gates, raised by `lifecycle_gate` events at the `tasks` and
`execution` boundaries, and the task gates, raised per `task_result` by its
severity; a high-severity build result becomes the run status
`needs_revision` and never reaches the workspace. Which Harness events feed
which gates was put to Patrick as three mappings. (1) Faithful: `plan
--accept` is `start_execution` at `approval`; the readiness checks are the
execution lifecycle gate, an unsupported control or missing information
`blocked`, an undispositioned high planning finding `chair_required`; the
build result is a task gate with approve, fix and retry, or acknowledge risk;
`receipt` is terminal. This changes the accept receipt's disposition and adds
a user step after the build, so envelopes, the golden table and the R2
journey all change. (2) Front-loaded: a lifecycle gate before the existing
acceptance gate, two gates at accept with nothing new in the second. (3) Wire
and walk: the host starts at `approval`; accept walks `start_execution`, the
execution lifecycle gate with the readiness checks as its receipts, then
`executing` and the synthetic task gate as today; readiness failures surface
as the `chair_required` and `blocked` stages instead of a `ValueError`;
envelopes, the golden table and the R2 journey are unchanged.

Patrick, September 23: "3 now, 1 later". Mapping 3 is step (b)'s second half,
in its own pull request with its own review pass, since the rename half
merged on the same go as steps (a) and (c). Mapping 1's task gate after the
build is a later decision, possibly by redefining R2's review step as that
gate; it is not scheduled. D23's decision 6 is amended by one: step (b) is
two pull requests, the rename and the stages.
