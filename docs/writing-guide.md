# Writing and entered-text guide

Use the [Google developer documentation style guide](https://developers.google.com/style)
for new or revised documentation and UI copy. This is the approved project
standard. The canonical all-project decision, its scope and approval provenance
are in the private archive's
[writing policy](https://github.com/Smart-AI-Memory/attune-private/blob/e6e53f6a092deb4536b63bc8609c2453a20e5a53/policy/writing-style.md).
The public rules below supply the applicable summary without requiring private
repository access.

## UI instructions

Use an action verb before a named control, with the control name in bold. Follow
[Google's UI-reference guidance](https://developers.google.com/style/ui-elements)
for capitalization and formatting. For next-action hints, the local convention
is **Next:** Click **Continue form**. Keep the verb in normal text. Use the exact
verified control for the documented build; this example is not a promise that
every screen has that control.

Write direct, descriptive instructions and labels. Preserve the distinction
between saving answers, accepting intent and authorizing execution. Refer to
named sections rather than screen position. Apply the standard to helper,
status, error, and approval text as well as tutorials.

## Entered text

Preserve users' wording and capitalization. Do not silently rewrite answers to
follow a writing convention. Any required normalization must be explicit.

Display ordinary prose in Attune's normal reading font during entry and review.
Use monospace for code, commands, paths and structured technical input, including
XML. Descriptive labels and spacing distinguish answers from instructions;
preserve meaningful line breaks and the established Attune visual style.

When documentation supplies literal text to enter, use
[code formatting](https://developers.google.com/style/code-in-text). That
convention does not prescribe the font of every input field.

## Apply the policy

Review changed copy against the relevant Google topic and the actual UI or
source. Record checked sources and dates when the decision depends on them.
Keep historical evidence historical and separate software checks from observed
human usability. This writing policy does not replace source-formatting rules
or grant merge, release, execution or provider authority.

See [AGENTS.md](../AGENTS.md) for project authority and private-context delivery.
Do not assume that every tool automatically reads repository instructions.
