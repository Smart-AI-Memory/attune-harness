## Delivery sequence

### Packaging recommendation: separate core, integrated product

**Recommendation, not a settled user decision:** create a separately installable harness library, with attune-ai as its first production integration. Modify attune-ai at its integration seams rather than rewrite its workflows. A separate library does not require a separate repository immediately; choose repository placement after the package-boundary experiment.

The migration direction strengthens the case for independence. The experiment must also demonstrate a direct user entry point into the new architecture, beyond attune-ai's wrapper. Existing owning specs remain sources of requirements and decisions; they do not require the future implementation to live forever in the current package. Record ownership transfers explicitly when moving a capability.

| New harness library owns | attune-ai continues to own |
|---|---|
| Portable task/attempt state, lifecycle, effect tracking, and evidence references | Developer workflows, cross-review/roundtable product behavior, and finding/disposition rules |
| Model/agent adapter contracts and capability qualification | Attune-family integration and host-facing experience |
| General extension lifecycle contracts and portable continuation | Repository governance, skill content/projections, help, and product configuration |

Dependency direction is attune-ai → harness core. The core must not import attune-ai; provider SDKs and concrete library integrations belong behind optional adapters. Reuse existing Attune-family public APIs instead of copying their implementations. This allocation is a design hypothesis, not a claim that the current code already separates cleanly.

**Basis:** current `pyproject.toml` couples attune-ai installation to Claude-specific SDKs and product dependencies; current roundtable source has a fixed roster. That supports investigating an independent boundary, but does not prove a separate package is cheaper than refactoring in place.

**Strongest counter-case:** a new library adds release, dependency, compatibility, and support work for a sole developer. If most changes require synchronized releases or the core repeatedly needs attune-ai internals, the split has failed to establish useful independence. A well-isolated internal module is the concrete alternative.

**Phase 1 boundary experiment:** run the same minimal fixture through (a) an isolated internal implementation and (b) a separately installed disposable core package. For the latter, use a clean environment without attune-ai or mandatory provider SDKs, a deterministic participant, and a tiny independent consumer. Then connect attune-ai through one public adapter using the same contract. Record dependency closures, integration-specific branches, duplicated logic, and files that must change together. The independent consumer tests separability, not market demand.

Favor the separate library if the clean install and both consumers work without core imports of attune-ai, duplicated domain machinery, or weakened portable behavior. If they fail, revise the boundary or keep the implementation internal provisionally. Do not migrate the workflow fleet or create a new repository merely to make the diagram true.

| 0 | Verified inventory and portable contract | Existing research | Requirements traced to current seams, state cases, and failure-sensitive probes |
