# Selected Voyage index and offline journey

Approved design of 2026-09-27 for the final Voyage implementation slice. The narrow per-invocation grant subset and deterministic unsigned runner builder are in scope. This document does not authorize a paid call or README qualification change.

## User outcome and existing boundary

A user who explicitly pins a signed Voyage plugin can build an immutable index, accept a retrieval selection, and retrieve/replay through that same selected bundle without a builtin-provider fallback. The host retains source selection, paid-stage journal, call budget, retrieval scope, result validation and publication authority. PR156 already handles selected embed/rerank through the host journal; `build_index` and `retrieve_voyage` currently call `refuse_dispatch` before creating state. PR157 removes that refusal only after selected preflight and exact path/tool checks. No selected path may call an injected `provider`, `VoyageProvider` or an attune-rag fallback.

The repository currently has **no real Voyage plugin runner artifact**: the signed PR155/156 tests build disposable ZIPs containing synthetic `main.py`; the only SDK code is host `VoyageProvider`. PR157 must include a small, reviewable, standalone runner source and manifest/packaging instructions for three entries (embed, rerank, index), with a scratch-key-signed fixture built from those exact source bytes. Ship a tiny top-level `attune_voyage_plugin` package in the Harness wheel with pure runner modules and an offline `python -m attune_voyage_plugin.bundle --output DIR` builder. The builder requires a nonexistent output directory (exclusive creation; no overwrite), deterministically copies only the runner modules into `code.zip` (fixed entry order, timestamp and permissions), writes `manifest.json` and `SKILL.md`, and reports the digest from Harness discovery; it does not sign, enable, register or accept anything. A user signs that digest with their chosen key, lists its public key and grant in a registry, enables it, and explicitly pins the observed full-section digest. The installed wheel can therefore produce the same reviewable source artifact as the checkout. Do not commit a maintainer-signed artifact or test trust root as if it were a release. The runner itself must not import Harness internals, because the child bootstrap admits only stdlib, signed ZIP and declared distribution closure.

## Boundaries and ordering

1. `inspect_selection` resolves the explicit complete-section registry pin and selected signed bundle. For a selected build, validate before making `index_dir`, generation directory or stage state. Reject an injected provider. Keep the unselected implementation and its config/digests unchanged. Completed published generation may be reused only after `check_generation` and selected authority recheck; it needs no key or `allow_provider` and launches no child. A selected retrieval checks its accepted selection/generation and source scope before creating a work directory, but a replay of a completed retrieval uses the existing cache with no credential/permission and no child.
2. Host `collect` and `embedding_batches` remain authoritative. `StageJournal.perform` obtains vectors through PR156's signed embed tool, replays completed stages, and retains `dispatching` on timeout/interruption/output limit. If a stage is unresolved, build stays unpublished; restart never re-dispatches it. Reuse of a prior generation still checks its metadata, source manifest and rows before copying unchanged embedding keys.
3. The host creates a generation-local, named `index_staging` directory that is neither the stage ledger nor its parent. Before any paid stage or index state, it computes a conservative row-byte bound from row count, vector width and source text sizes and checks that the accepted result grant can hold the largest planned embedding batch; it also enforces the exact serialized 64 MiB limit before writing `rows.json`. The rows contain expected passage IDs, repository/path/text, embedding keys and vectors normalized to the frozen float32 index representation; raw paid-stage results and receipts stay unchanged. The small index-tool arguments contain the generation ID, row count and rows digest, not a potentially >1 MiB row array. The selected bundle's declared and accepted path grant must name `index_staging`; a missing grant refuses before any index child. Neither paid embed/rerank nor index child gets a ledger/stage record path through `paths`.
4. A **separate `VoyageIndexContext`** is formed inside the host's index-owner lease and holds normalized config digest, generation, selected extension/artifact and explicit index local tool name, staging path and expected row digest/count. It checks the host generation manifest and unpublished state, staging containment/no symlink, current registry pin and registration state. A same-process context is a cooperation guard, not independent proof that an OS lease is held. `run_voyage_index` alone may execute that network-declaring bundle's index role; it is not a paid-stage context and never claims `dispatching`. The ordinary generic network `run` remains closed. The index child receives only the accepted `index_staging` path and scratch, no `VOYAGE_API_KEY`; the host pre/post checks the manifest, stage ledger and every stage record plus selected registry/registration/bundle. These are cooperating-code checks, not an OS sandbox against arbitrary same-user filesystem access.
5. Bundle-wide grant conflict needs an explicit *narrowing* rule: the accepted bundle grants may include both `VOYAGE_API_KEY` and `index_staging`, but PR156's paid adapter currently passes `paths={}` and private `_run` requires every granted path, while `environment()` would otherwise require the secret for a local index. Root approved the two Voyage-specific callers selecting an invocation subset of the already accepted grant: paid roles use the secret and no index path; index uses `index_staging` and no secret. Validate subset against the accepted grant, record both accepted and applied grants, and leave generic `run` unchanged. The receipt distinguishes declared network from actual invocation authority. This cannot widen network authority: selected contexts, accepted exact `api.voyageai.com` declaration, and the per-paid-call `allow_provider` still gate paid dispatch. Refusing a bundle that omits `index_staging` is preferable to silently adding it or repinning the registry. This is not a per-tool sandbox or security claim.
6. The signed index entry writes LanceDB only under `index_staging/db`, using the already qualified `lancedb` closure and the frozen no-stem/no-stop/no-fold FTS profile. Its result file reports row count/digest but cannot publish. The host rereads `rows.json` and validates the staged tree has no symlinks, nonregular entries or unexpected files/paths, opens `passages`, verifies the exact Arrow passage/vector schema and every row equals the expected sorted float32 row, checks the FTS index’s recorded tokenizer settings, and probes dense and FTS searches where rows exist, and independently computes `rows_digest`. On mismatch or changed host evidence it leaves the generation unpublished and writes a bounded host-owned index error receipt for inspection. `db` moves into the generation only after validation; `build-receipt.json` and `published.json` are host-written, with the publication marker last. Restart rejects any retained index error, preserves the existing manifest byte-for-byte, and revalidates pre-dispatch host evidence and selected artifact before considering a complete interrupted staging/DB. It never blindly overwrites or deletes staging and never repeats a paid stage. Source and selection checks repeat immediately before publication.
7. Retrieval uses existing host `candidates`, `ranking`, `validate_evidence`, cache and scope controls. With a selected config, it runs only PR156's signed embed/rerank tools for new paid stages. Published generation and final cache replay remain possible with no key/`allow_provider`; any fresh paid stage still requires both. A changed pin/disabled/revoked bundle refuses before work-state creation; no fallback. The host does not present ranking as answer verification.

## Real runner source and offline probes

The narrow runner should have separate signed ZIP entries (for example `voyage_runner.embed`, `.rerank`, `.index`) with a shared request/result helper. Embed/rerank freeze `voyage-code-4`, 1024 float dimensions, `rerank-2.5`, truncation disabled, the endpoint `https://api.voyageai.com/v1`, timeout and retries/redirect behavior as the current host provider, and raw response index/usage checks before emitting normalized JSON. The index entry reads only the named staging rows and uses LanceDB. A manifest template declares exactly `api.voyageai.com`, direct `voyageai`/`lancedb` imports, the three run roles, `VOYAGE_API_KEY`, `index_staging`, scratch/time/output, and explicit path usage; tests package and sign these source bytes with disposable scratch keys. No live key is needed to inspect, index locally, or replay.

- Signed offline fixture: full plan → accepted pin → selected build → selection → scoped query → signed embed/rerank → cache replay. Compare host stage IDs/status/results/usage and index row digest to an unselected in-process fake-provider run, discounting the selected config/generation identity and process timing. Assert the three accepted role names actually run; poison builtin providers/fallbacks.
- Update base generation after source edits/deletions; verify unchanged vectors reused, removed passages absent, no extra paid calls, and selected index tool reruns only for a genuinely new generation. Empty corpus/index and no-result scope keep zero paid calls.
- Missing pin/grant/key/permission, wrong path/tool/kind/rows digest, changed registry/registration or guarded host evidence refuse before launch or publication. A signed child that tampers with `rows.json`, writes symlinks/extra rows, omits FTS, returns malformed JSON, or modifies stage receipts leaves generation unpublished and inspectable. No child request includes ledger paths or secret value in serialized records.
- Kill/timeout/output-limit during paid embed or rerank retains its `dispatching` stage; another build/retrieval call refuses re-dispatch. A local index child interruption leaves staging unpublished; a later run only validates complete staged output or requires explicit inspection, never repeats paid stages.
- Test the **real runner source** separately with offline SDK transport stubs for model, endpoint, response-index, redirect/retry, timeout and usage behavior. Execute its actual index entry in a signed child against real offline LanceDB, not a fake table. The signed end-to-end fixture uses synthetic provider results and proves software wiring only. It does not establish live Voyage equivalence, answer accuracy or R6's required live differential.
